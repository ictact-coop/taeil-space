## 1. 문서 분석 결과

### 1.1 핵심 도메인 규칙 (구현 시 반드시 지킬 것)

1. **신청은 결제가 끝나야 접수된다.** 이용자가 신청서를 제출하면 곧바로 결제 단계로 넘어가고, 결제가 완료되어야 "신청접수"가 된다. 전액 감면(0원)인 건은 PG를 거치지 않고 바로 신청접수된다.
2. **예약확정은 관리자 승인 시점에 생긴다.** 이미 결제된 신청을 관리자가 심사해서 승인하면 예약확정, 반려하면 **자동으로 전액 환불**된다. *([요구] 3·6·7장의 "승인 → 결제 → 확정"과 반대 순서이며, 발주처 결정 v0.2에 따른 것)*
3. **결제를 시작하는 순간부터 일정을 임시 확보한다.** 결제 유효시간(정책값, 예: 30분) 동안만 확보하고, 그 안에 결제하지 않으면 자동으로 풀어준다. 결제된 신청은 심사가 끝날 때까지 확보를 유지하고, 승인되면 확정, 반려·철회되면 해제한다. 따라서 **같은 공간·같은 시간에는 먼저 결제한 신청 한 건만** 심사에 올라간다.
4. **같은 공간·같은 시간의 확보·확정·자체행사·휴관이 겹치는 것은 DB 수준에서 막는다**(8장, AT-10).
5. **결제완료는 PG 웹훅이나 서버 측 결제 조회로만 판정한다.** 브라우저가 돌려주는 결과만 믿지 않는다. 주문번호 단위로 멱등성을 보장한다(17장).
6. **금액 스냅샷**: 결제할 때 계산한 금액을 신청 건에 남기고, 요금표는 버전으로 관리한다(16장, [WF] 12쪽).
7. **감사 로그**: 관리자가 상태·금액·환불을 수동으로 바꾸면 변경 전후 값, 처리자, 시각, 사유를 남긴다(8장, AT-11).
8. **단체는 고유번호 또는 사업자등록번호로 판별한다.** BR-03(단체당 1일 1건)과 BR-04(6개월 횟수)는 이 번호를 기준으로 센다(아래 2.5).
9. **공휴일·휴관일은 모두 관리자 설정이다.** BR-01("매주 월요일, 1월 1일, 설·추석 당일")을 코드에 넣지 않고, 설정 데이터의 초기값으로만 넣는다(아래 2.6).
10. **나머지 정책도 설정값으로 둔다**: 신청기한, 1일 1건, 6개월 횟수, 시간 단위, 완충시간, 결제 유효시간, 환불률 등([WF] 14쪽 설계 원칙).

## 2. 시스템 설계 방향

### 2.1 기술 스택 (제안 — 저장소가 비어 있어 새로 정함)

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | **Next.js (App Router) + TypeScript**, 이용자·관리자를 하나의 앱에서 운영(`/`, `/admin`) | 소규모 운영 조직에 맞게 배포 단위를 하나로. 라우트 핸들러로 PG 웹훅 처리 |
| DB | **PostgreSQL 16** + `btree_gist` | `EXCLUDE USING gist (space_id WITH =, during WITH &&)`로 이중 예약을 DB가 직접 차단 |
| ORM | Drizzle ORM (+ 배제 제약은 SQL 마이그레이션) | SQL에 가깝게 쓸 수 있고, 제약·트랜잭션을 명시적으로 제어 가능 |
| 작업 큐 | **pg-boss** (Postgres 기반) | 결제 유효시간 만료, 보완기한 만료, 반려 시 환불 재시도, 이용완료 처리, 개인정보 파기 배치 |
| 결제 | **PortOne V2** (그 아래 PG사는 계약에 따라 선택) | PG사가 정해지기 전에도 연동 개발 가능. 결제·조회·취소(부분환불)·웹훅 서명 지원 |
| 알림 | 이메일: AWS SES 또는 NHN Cloud / LMS: NHN Cloud·솔라피 등 | 공급자를 바꿀 수 있는 어댑터 구조. 알림톡은 2차 |
| 파일 | S3 호환 객체 저장소 + 서명된 URL + ClamAV 검사 | 첨부파일 악성 여부 검사·접근 제어 |
| 인증 | 이용자: 휴대전화/이메일 OTP + 신청번호, 관리자: 아이디·비밀번호 + TOTP 2단계 인증 | [요구] 3장, NFR-05 |
| 인프라 | 국내 리전(AWS 서울 또는 NCP), 관리형 DB, 매일 백업 + PITR | 개인정보 국내 보관, NFR-07 |
| 품질 | Vitest(도메인 로직), Playwright(E2E·모바일 뷰포트), axe(접근성) | 인수 테스트(5장)를 자동 테스트로 만들어 둠 |

### 2.3 상태 모델 (v0.2: 신청 시 결제 → 승인 → 확정)

```
작성중 ─제출→ 결제대기 ─┬─결제성공(웹훅/조회)→ 신청접수
   (일정 임시확보,      ├─(0원) 제출 즉시→ 신청접수
    결제 유효시간)      └─유효시간 만료·결제 포기→ 미결제취소 (일정 해제)

신청접수 ─담당자 확인→ 검토중 ─┬─보완요청→ 보완요청 ─재제출→ 검토중
                              │                 └─보완기한 만료→ 신청종료* → 전액 환불
                              ├─반려→ 반려 → 전액 자동 환불
                              └─승인→ 예약확정

신청접수·검토중·보완요청 ─이용자 철회→ 신청취소* → 승인 전 환불 규정(기본 전액)
예약확정 ─이용자 취소→ 취소요청 ─┬─환불성공→ 환불완료
                                 └─환불률 0%→ 취소완료*
예약확정 ─기념관 사정 취소(관리자, 사유 필수)→ 전액 환불 → 환불완료
예약확정 ─이용 종료(배치)→ 이용완료
(* 는 요구사항에 없어 새로 제안한 상태)
```

- **신청 상태와 결제·환불 상태는 분리해서 관리한다.** 신청은 "반려"로 끝나도 환불은 `refunds` 테이블에서 요청 → 성공/실패로 따로 진행하고, 실패하면 A-06 재처리 목록에 나타난다. 이렇게 해야 "반려했는데 환불이 안 된" 건을 놓치지 않는다.
- 상태를 바꾸는 코드는 `reservation/transition()` 한 곳에서만 실행하고, 같은 트랜잭션 안에서 **감사 로그 기록 + 알림·환불 작업 등록(아웃박스)**까지 처리한다.
- 일정 점유 테이블 `slot_occupancies(space_id, during tstzrange, kind, application_id, expires_at)`
  - `kind ∈ {PENDING_PAYMENT(결제대기, 만료 시각 있음), HELD(결제완료·심사중), CONFIRMED(예약확정), BLOCK(자체행사·점검·임시차단)}` 행에 배제 제약을 건다.
  - 만료된 PENDING_PAYMENT 행은 배치가 지우고, 새 신청이 들어올 때도 같은 트랜잭션 안에서 만료분을 먼저 정리해서 일정이 필요 이상 막히지 않게 한다.
  - 이용자 달력에서는 PENDING_PAYMENT·HELD를 "신청진행", CONFIRMED를 "예약완료", BLOCK과 휴관일을 "대관불가"로 표시한다(단체명은 공개하지 않음).
  - 준비·철수 완충시간은 `during` 범위를 앞뒤로 늘려서 저장한다.
- **보완요청 때 고칠 수 있는 범위**: 이미 결제한 금액과 맞아야 하므로 기본적으로 *금액이 바뀌지 않는 항목*(행사 내용, 첨부, 연락처, 인원(정원 안에서))만 고칠 수 있게 한다. 공간·일시를 바꾸려면 철회하고 다시 신청해야 한다(P-14).

### 2.5 단체 판별 (고유번호·사업자등록번호)

- **입력**: 신청서에 "고유번호 또는 사업자등록번호" 칸을 두고, 번호 종류(고유번호 / 사업자등록번호)를 고르게 한다. 두 번호 모두 10자리(`XXX-XX-XXXXX`) 형식이다.
- **검증**: 하이픈을 빼고 숫자 10자리로 정규화한 뒤 형식을 검사하고, 사업자등록번호는 검증번호(마지막 자리 체크섬)도 확인한다. 고유번호에도 같은 체크섬을 적용할지는 실제 번호 샘플로 확인하고 정한다. 국세청 사업자등록 상태조회 API(공공데이터포털)로 휴·폐업 여부를 확인하는 기능은 선택 사항이다.
- **판별**: `organizations.reg_no`(정규화된 번호)에 유일성 제약을 건다. 같은 번호로 들어온 신청은 같은 단체로 보고 BR-03(같은 날 1건)과 BR-04(6개월 횟수)를 센다. 단체명은 신청마다 달라도 되는 표시용 값으로만 쓴다.
- **번호가 없는 경우**(개인, 임의단체 등): 번호를 필수로 할지는 P-03에서 정한다. 필수가 아니라면 번호 없는 신청은 자동 판별을 하지 않고, 심사 화면에 "단체 번호 없음 — 중복 여부 수동 확인"으로 표시한다. 이때 같은 인증 휴대전화로 들어온 이전 신청을 참고용으로 함께 보여준다.
- **관리자 기능**: 심사 화면(A-04)에 같은 번호의 이전 신청·이용 내역과 6개월 사용 횟수를 보여준다. 번호를 잘못 입력한 건은 관리자가 고칠 수 있고, 이 수정은 감사 로그에 남긴다.

### 2.6 공휴일·휴관일 설정

BR-01을 코드에 고정하지 않고, 관리자가 A-09 일정 관리에서 다음 규칙을 등록한다.

| 규칙 유형 | 예시 | 적용 범위 |
|---|---|---|
| 정기 휴관 요일 | 매주 월요일 | 전체 또는 공간별 |
| 매년 같은 날 | 1월 1일 | 전체 또는 공간별 |
| 특정 날짜·기간 | 2027 설 당일, 추석 당일, 임시 휴관, 시설 점검 기간 | 전체 또는 공간별 |
| 예외 개관일 | "월요일이지만 이날은 개관" | 위 규칙들보다 우선 |

- 각 규칙에 이름, 사유, 적용 시작·종료일, 이용자에게 보여줄 문구("휴관일입니다" 등)를 둔다. 이용자가 해당 날짜를 누르면 이 문구가 나온다(AT-01).
- 우선순위: 예외 개관일 > 특정 날짜·기간 > 매년 같은 날 > 정기 휴관 요일.
- 시간 단위 차단(자체행사·점검 몇 시간)은 기존 `schedule_blocks`로, 하루 전체 휴관은 `closure_rules`로 처리한다.
- **초기 데이터**: 월요일 휴관, 1월 1일, 2026~2027년 설·추석 당일을 시드로 넣는다. 공공데이터포털 특일 정보 API에서 연도별 공휴일을 불러와 **관리자가 확인한 뒤 등록**하는 버튼은 선택 기능이다(자동 등록은 하지 않음).
- 이미 신청·확정된 날짜에 휴관 규칙을 새로 넣으면 저장 전에 겹치는 신청 목록을 경고로 보여준다. 기존 신청은 자동으로 취소하지 않는다.

### 2.7 정책 설정 체계 (v0.3)

정책 결정 사항의 대부분을 관리자 설정 페이지에서 조정한다(항목 목록은 4장). 설정은 다음 원칙을 따른다.

- **설정 정의는 코드에, 값은 DB에**: 코드에 각 설정의 키, 자료형, 기본값, 허용 범위, 설명, 그룹을 정의한다. 관리자는 값만 바꾼다. 화면은 이 정의를 읽어 자동으로 그린다.
- **값은 버전으로 쌓는다**: 모든 값에 적용 시작일이 있다. 미래 날짜로 변경을 예약할 수 있고(예: "11/1부터 요금 변경"), 이전 버전으로 되돌릴 수 있다. 덮어쓰지 않는다.
- **이미 결제한 신청은 설정을 바꿔도 달라지지 않는다**: 결제 시점의 요금표·감면·환불 규정 버전을 신청 건에 스냅샷으로 남긴다. 이용자가 동의한 규정이 그대로 적용된다.
- **휴관·차단·신청 규칙은 새 신청에만 적용한다**: 이미 들어온 신청과 겹치면 저장 전에 경고 목록을 보여주고, 기존 신청을 자동으로 취소하지는 않는다.
- **저장할 때 검증한다**: 환불률은 0~100%, 이용일이 가까울수록 환불률이 같거나 낮아야 함, 시간 단위가 운영시간을 나누어떨어지게, 요금표 적용기간이 겹치지 않게 등.
- **변경 사유는 필수, 감사 로그에 남긴다**: 누가, 언제, 무엇을, 이전 값 → 새 값, 사유.
- **권한**: 수정은 시스템 관리자만 한다. 대관 담당자는 휴관·일정 차단·교육실 접수기간만 수정할 수 있다. 회계 담당자는 조회만 한다.

## 3. 구현 순서 (v0.3)

### 3.1 순서를 정한 원칙

1. **설정 저장소를 가장 먼저 만든다.** 규칙 엔진, 요금, 환불, 배치 작업이 모두 설정값을 읽으므로, 설정이 없으면 다른 기능을 만들 수 없다.
2. **관리자 설정 → 이용자 신청 → 결제 → 심사 순서로 만든다.** 공간·휴관일·요금이 먼저 들어가 있어야 이용자 화면을 실제 데이터로 테스트할 수 있다.
3. **PG는 계약을 기다리지 않는다.** PortOne 테스트 채널은 계약 전에도 쓸 수 있으므로 테스트 모드로 먼저 완성하고, 계약이 끝나면 라이브 키만 바꾼다.
4. **오픈에 꼭 필요한 것과 오픈 직후에 필요한 것을 나눈다.** 신청기한이 "이용일 최소 2주 전"이고 심사에 3~7일이 걸리므로, 오픈 첫날 받은 예약의 이용일은 빨라도 2주 뒤다. 따라서 *확정된 예약의 취소·환불, 이용완료 처리, 예약확인서*는 오픈 뒤 2주 안에만 끝내면 된다. 반면 *반려 환불, 승인 전 철회 환불*은 오픈 첫 주부터 생길 수 있으므로 오픈 전에 있어야 한다.
5. **단계마다 스테이징에서 시연할 수 있는 상태로 끝낸다.**

```
0 기반 ─→ 1 설정 페이지 ─→ 2 이용자 신청 ─→ 3 결제·심사 ─→ 4 오픈 준비 ─→ 🚩 오픈 ─→ 5 오픈 후 2주 ─→ 6 고도화
                  └── 10/13: 발주처가 설정 화면에서 초기값 입력          └── 10/22: PG 라이브 전환 판단
```

## 5. 테스트·검수 전략

- **설정 테스트**: 설정 검증 규칙, 적용일 기준 버전 조회, 설정을 바꿔도 결제된 신청의 금액·환불률이 그대로인지.
- **도메인 단위 테스트**: 규칙 엔진(BR-01~08), 휴관 규칙 우선순위, 단체번호 정규화·검증, 요금 계산, 환불 계산, 상태 전이 가드. 정책값을 바꿔 가며 테스트한다.
- **DB 동시성 테스트**: 같은 슬롯에 결제 시작 요청을 동시에 N건 보내도 1건만 일정을 확보하는지.
- **결제 시나리오**: 웹훅 먼저 도착 / 브라우저 복귀 먼저 / 웹훅 중복 / 웹훅 유실(→ 조회로 재확인) / 결제 유효시간이 끝난 뒤 늦게 결제 성공(→ 일정이 이미 풀렸으면 자동 환불) / 반려 후 자동 환불 실패 → 재처리 / 부분환불 누적 한도.
- **E2E(Playwright)**: 인수 테스트를 시나리오로 자동화하고, 모바일 뷰포트에서 조회 → 신청 → 결제 → 승인 → 확인까지 한 번에 확인.
- **요구사항 추적표**: `docs/traceability.md`에서 [요구] ID ↔ 화면 ↔ API ↔ 테스트를 관리([요구] 30장 산출물).

| 위험 | 영향 | 대응 |
