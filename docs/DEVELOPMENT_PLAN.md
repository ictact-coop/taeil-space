## 1. 문서 분석 결과

### 1.1 핵심 도메인 규칙 (구현 시 반드시 지킬 것)

1. **예약확정은 결제 완료 시점에만 생긴다.** 관리자 승인은 결제를 허락할 뿐이다([요구] 3장, [WF] 2쪽, [시안] 5쪽). 전액 감면(0원)인 건만 PG 없이 승인 즉시 확정된다([요구] 16장).
2. **결제대기부터 일정을 임시 확보한다.** 결제기한(기본 48시간, 연장 가능)이 지나면 자동으로 취소하고 일정을 다시 연다(AT-06, AT-08).
3. **같은 공간·같은 시간의 확정 예약과 자체행사가 겹치는 것은 DB 수준에서 막는다**(8장, AT-10). 애플리케이션 검증만으로는 부족하다.
4. **결제완료는 PG 웹훅이나 서버 측 결제 조회로만 판정한다.** 브라우저가 돌려주는 결과만 믿지 않는다. 주문번호 단위로 멱등성을 보장한다(17장, AT-07).
5. **금액 스냅샷**: 신청할 때 계산한 금액과 승인할 때 확정한 금액을 예약 건에 남기고, 요금표는 버전으로 관리한다(16장, [WF] 12쪽).
6. **감사 로그**: 관리자가 상태·금액·환불을 수동으로 바꾸면 변경 전후 값, 처리자, 시각, 사유를 남긴다(8장, AT-11).
7. **정책은 설정값으로 둔다**: 휴관일, 신청기한, 1일 1건, 6개월 횟수, 시간 단위, 완충시간, 결제기한, 환불률, 동시신청 허용 여부 등([WF] 14쪽 설계 원칙).

## 2. 시스템 설계 방향

### 2.1 기술 스택 (제안 — 저장소가 비어 있어 새로 정함)

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | **Next.js (App Router) + TypeScript**, 이용자·관리자를 하나의 앱에서 운영(`/`, `/admin`) | 소규모 운영 조직에 맞게 배포 단위를 하나로. 서버 액션·라우트 핸들러로 PG 웹훅 처리 |
| DB | **PostgreSQL 16** + `btree_gist` | `EXCLUDE USING gist (space_id WITH =, during WITH &&)`로 이중 예약을 DB가 직접 차단(요구 8장) |
| ORM | Drizzle ORM (+ 배제 제약은 SQL 마이그레이션) | SQL에 가깝게 쓸 수 있고, 제약·트랜잭션을 명시적으로 제어 가능 |
| 작업 큐 | **pg-boss** (Postgres 기반) | 결제기한 만료, 기한 임박 알림, 이용완료 처리, 개인정보 파기 배치. Redis를 따로 두지 않아도 됨 |
| 결제 | **PortOne V2** (그 아래 PG사는 계약에 따라 선택) | P-09(PG사 미정)가 정해지기 전에도 연동 개발을 시작할 수 있음. 결제·조회·취소(부분환불)·웹훅 서명 지원 |
| 알림 | 이메일: AWS SES 또는 NHN Cloud / LMS: NHN Cloud·솔라피 등 | 채널별 어댑터 인터페이스로 공급자를 바꿀 수 있게 설계. 알림톡은 2차 |
| 파일 | S3 호환 객체 저장소 + 서명된 URL + ClamAV 검사 | 첨부파일 악성 여부 검사·접근 제어([요구] 23장) |
| 인증 | 이용자: 휴대전화/이메일 OTP + 예약번호, 관리자: 아이디·비밀번호 + TOTP 2단계 인증 | [요구] 3장, NFR-05 |
| 인프라 | 국내 리전(AWS 서울 또는 NCP), 관리형 DB, 매일 백업 + PITR | 개인정보 국내 보관, NFR-07 |
| 품질 | Vitest(도메인 로직), Playwright(E2E·모바일 뷰포트), axe(접근성) | AT-01~12를 자동 테스트로 만들어 둠 |

### 2.2 모듈 구성

```
src/
  domain/            # 프레임워크와 무관한 순수 도메인 로직(테스트 대상 1순위)
    rules/           #   BR-01~08 규칙 엔진 (입력: 신청안 + 정책값 → 위반 목록)
    pricing/         #   요금 계산(요금표 버전, 감면, 스냅샷)
    refund/          #   환불률·환불 가능 금액 계산
    reservation/     #   상태 머신·전이 가드
  server/
    db/              # 스키마·마이그레이션(배제 제약 포함)
    payments/        # PortOne 어댑터, 웹훅 검증, 결제 조회 재확인
    notifications/   # 템플릿 렌더링, 이메일/LMS 어댑터, 발송 이력
    jobs/            # pg-boss 작업(결제기한 만료, 기한 임박 알림, 이용완료, 파기)
    audit/           # 감사 로그 기록기
  app/
    (public)/        # U-01~U-10
    admin/           # A-01~A-12
```

### 2.3 상태 모델 ([요구] 7장 + 1.2 G-7 보완)

```
작성중 ─제출→ 신청접수 ─확인→ 검토중 ─┬─보완요청→ 보완요청 ─재제출→ 검토중
                                      │                └─기한만료→ 신청종료*
                                      ├─반려→ 반려
                                      └─승인→ 결제대기 ─┬─결제성공(웹훅/조회)→ 예약확정
                                                        ├─(0원) 승인 즉시→ 예약확정
                                                        └─기한만료→ 미결제취소
신청접수·검토중·보완요청·결제대기 ─이용자 철회→ 신청취소*
예약확정 ─이용자 취소→ 취소요청 ─┬─환불성공→ 환불완료
                                 ├─환불률 0%→ 취소완료*
                                 └─환불실패→ (재처리 목록, 상태 유지)
예약확정 ─기념관 사정 취소(관리자)→ 전액 환불 → 환불완료  (사유 필수)
예약확정 ─이용 종료(배치)→ 이용완료
(* 는 요구사항에 없어 새로 제안한 상태)
```

- 상태를 바꾸는 코드는 `reservation/transition()` 한 곳에서만 실행하고, 같은 트랜잭션 안에서 **감사 로그 기록 + 알림 작업 등록(아웃박스)**까지 처리한다.
- 일정 점유 테이블 `slot_occupancies(space_id, during tstzrange, kind, application_id)`
  - `kind ∈ {HOLD(결제대기), CONFIRMED, BLOCK(자체행사·점검·휴관)}` 행에 배제 제약을 건다.
  - 신청접수·검토중 단계에서 일정을 점유할지는 정책값 P-04에 따라 정한다. 기본값은 "점유 안 함, 달력에 '신청진행'으로만 표시"
  - 준비·철수 완충시간은 `during` 범위를 앞뒤로 늘려서 저장한다.

### 2.4 주요 엔터티 ([요구] 22장 기반)

`spaces`, `space_operating_hours`(기간별), `schedule_blocks`, `booking_windows`(교육실 접수 공개기간), `policies`(키-값 + 적용기간), `fee_tables` / `fee_items`(버전), `discount_rules`, `applicants`(인증된 연락처 기준), `applications`, `application_status_history`, `slot_occupancies`, `price_snapshots`, `attachments`, `payments`(신청 1건에 여러 번 시도 가능), `refunds`, `notification_templates`, `notification_logs`, `admin_users` / `roles`, `audit_logs`(추가만 가능, 수정·삭제 불가), `pii_access_logs`

10월 안에 PG까지 모두 갖추려면 **9/30까지 P-01·P-06·P-09 확정 + PG 계약 완료**가 필요하다. 현재 문서 상태(정책 "미정")로 보면 실현 가능성이 낮다. 이 경우 오픈 목표를 11월 중순으로 옮기는 것이 현실적이다.

## 5. 테스트·검수 전략

- **도메인 단위 테스트**: 규칙 엔진(BR-01~08), 요금 계산, 환불 계산, 상태 전이 가드. 정책값을 바꿔 가며 테스트한다.
- **DB 동시성 테스트**: 같은 슬롯에 확정 요청을 동시에 N건 보내도 1건만 성공하는지(AT-07·10).
- **결제 시나리오**: 웹훅 먼저 도착 / 브라우저 복귀 먼저 / 웹훅 중복 / 웹훅 유실(→ 조회로 재확인) / 부분환불 누적 한도.
- **E2E(Playwright)**: AT-01~12를 시나리오로 자동화하고, 모바일 뷰포트에서 조회 → 신청 → 결제 → 확인까지 한 번에 확인(AT-12).
- **요구사항 추적표**: `docs/traceability.md`에서 [요구] ID ↔ 화면 ↔ API ↔ 테스트를 관리([요구] 30장 산출물).
